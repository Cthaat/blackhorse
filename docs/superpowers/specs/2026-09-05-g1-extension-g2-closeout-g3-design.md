# G1 扩展、G2 收尾与 G3 维护主线设计

状态：用户已选定开发范围与顺序；以下新增业务规则为建议设计，待书面确认。不是代码完成记录。

## 执行顺序与范围

1. G1 扩展：EXT-11 黑名单／爽约限制、EXT-35 申诉、EXT-01 二维码资产管理。
2. G2 小范围收尾：历史投递积压与 Element Plus 警告定位；真实重启、执行中取消与普通角色权限的最小验证，修复实际发现的问题。
3. G3.1～G3.3：EXT-06 维护／校准计划与执行，EXT-36 维修／整改／维护 SLA。

保持当前仓库与分支、Spring Boot 模块化单体、原生 MySQL／Redis、既有 Vue 工作台。保留用户文件和演示数据，迁移前备份；分批提交推送，不创建工作树。培训考试、AI、IoT、支付、MQ、微服务不在本轮范围。

## 方案取舍

- 推荐：新增领域记录与统一校验服务，复用预约、维修、附件、消息、追溯和任务基础；分别交付可运行的垂直业务闭环。
- 不采用仅靠账号禁用／黑名单布尔字段：无法表达实验室范围、期限、事实与申诉，且妨碍用户查看记录和申诉。
- 不采用信用分引擎或通用工作流平台：目前不需要积分、任意规则脚本或自由流程编排，避免扩大范围。

## 第一批：限制与申诉

### 业务规则（建议默认值）

- 手工黑名单限制到具体实验室；管理员只能管理自身实验室范围，必须填写原因与结束时间，期限 1～365 天。不可给自己创建或解除限制。它是预约业务限制，不是账号禁用。
- 爽约沿用已批准预约超过领用宽限期转为 NO_SHOW 的现有事实。默认每次新爽约限制该实验室新增预约 7 天，期限允许配置为 1～90 天；本期不做累计信用分。
- 自动规则使用不可变发布版本，记录命中版本、来源预约、事实时间、范围和起止时间；修改规则不重算既有处罚。启用前历史爽约只保留历史，不自动追罚。
- 同一爽约事实最多生成一条限制；重复调度与恢复不延长期限。多条有效限制取联合效果，解除其中一条不误解除其他条。
- 普通预约、代办、候补加入／递补／确认使用同一限制判定；受限时保留登录、查询、取消、归还、报修及申诉能力。
- 不静默取消既有预约，不中断正在使用的设备。已批准未领用预约在领用时检查当前限制并提示原因；待处理事项允许授权管理人员显式处置。
- 本人可以对手工限制或爽约限制提交一次申诉，填写说明并关联有权的私有证据附件。申诉中不自动解除限制；管理员审批必须填写理由，不得自审。批准撤销对应限制但保留原爽约与审核历史；驳回不延长期限。已到期记录仍可申诉纠正事实评价，但不会恢复预约占用。

### 数据、接口与前端

- 独立限制规则版本、限制事实、申诉、审核历史；来源事实唯一约束，命令使用状态条件更新，写入事实／审计与业务变更同事务。
- 用户维度串行化限制变更和受限预约操作；遵循统一锁顺序，不在设备锁内新增反向锁路径。处理跨设备并发，不能只用前端按钮或 Redis 缓存阻断。
- API 分为本人列表／详情／申诉，以及授权范围的规则发布、限制登记／解除、申诉审核。正整数 ID、有限分页、长度／时间范围校验；所有查询和附件下载重新检查对象范围。
- 学生页面：我的限制与申诉、原因／期限／状态／处理记录；设备预约和候补入口显示可理解的拒绝原因。
- 管理页面：限制列表、手工登记／解除、规则版本、申诉审核与业务追溯。系统管理角色不因新增菜单自动获取业务对象数据权限。
- 限制与审核通知接入 G2 持久消息渠道；来源事实可补登，重复执行不重复通知，不允许通过通知重放改变处罚或审批结果。

## 第二批：二维码资产管理

- 设备详情提供单张标签与受控批量打印（最多 100 张），展示资产编号、设备名称与二维码。二维码只包含本项目设备定位链接，不含 token、个人信息或操作授权。
- 扫码落到项目内的设备入口，未登录走正常登录并安全回跳；预约、报修和管理员领还核验分别调用已有授权接口。扫码不会自动批准、领出或归还。
- 支持手机系统相机扫描及站内扫码入口；站内识别仅接受本项目设备链接格式，不执行任意外部跳转。相机权限拒绝或 HTTP 非安全环境时明确提示并提供资产编号查询替代。
- 默认本机地址仅本机可访问；不自动把服务暴露到局域网，也不声称手机能访问 127.0.0.1。标签地址配置需校验允许的项目源，配置局域网／HTTPS 属于显式部署步骤。

## 第三批：G2 小范围收尾

- 先重新检查两条历史重试积压及失败事实，区分合法等待、数据缺失与代码错误；不直接删除记录或改成送达。需要更改无法恢复的历史业务事实时另行说明。
- 定位 Element Plus 警告，仅修复确定的调用问题，不开展整体界面重做。
- 隔离数据下验证实际进程停止与恢复、执行中合作式取消、普通角色下载撤权；保留已提交导入行，结果使用真实状态。只补相关回归，不扩大为全角色 E2E 或压测。

## 第四批：G3.1～G3.3 设计边界

### G3.1 维护／校准计划

- 按设备设置维护或校准类型、周期天数、首次到期时间、负责人、启停与说明；修改留版本，已生成工单保留原快照。
- 展示计划列表、临期／逾期工作台和设备维护档案。有效校准报告沿用私有附件权限。

### G3.2 维护执行

- 以计划及周期到期点为唯一键生成工单，复用维修派单／处理／验收能力，明确区分故障维修与计划维护／校准来源。
- 完成一个周期后以验收完成时间计算下一周期；未完成不无限生成积压工单，停用计划不删除历史或自动取消已生成工单。
- 计划到期不直接停机。安排停用窗口时，与预约及候补占位使用同一设备仲裁；存在有效冲突时拒绝生效并展示有权的影响清单，由管理员显式处理后重试。
- 待处理停用窗口阻断相交的新预约；设备使用中不得自动进入维护。执行完成仍需授权验收，恢复可用必须检查其他维修、维护及安全阻断，不允许覆盖其他不可用原因。

### G3.3 SLA

- 覆盖维修、维护和隐患整改；按类型／风险配置响应与处理期限，规则版本及命中截止时间留快照，使用连续自然时长，本期不引入工作日历。
- 由明确业务动作记录首次响应、开始处理、完成与关闭；只有授权管理人员能记录原因并暂停／恢复处理计时，暂停不解除安全阻断，不允许无痕改截止时间。
- 临期、逾期和升级使用稳定阶段标识防重；默认临期为剩余时长不超过总期限的 20%，到期提醒责任人，逾期 24 小时升级范围内管理人员。每个阶段最多登记一次，关闭后不继续产生告警。
- 前端提供临期／逾期队列、截止时间、责任人、暂停原因和升级时间线；复用 G2 站内投递，外部消息保持关闭。不因超时自动验收或销号。

## 验收与开发约束

- 每批先实现后端约束及最小定向测试，再接通完整页面并做相关联调；不以编译通过代替权限或一致性验证。
- 第一批至少验证：重复爽约不重复限制、到期边界、多限制叠加、申诉自审／越权拒绝、批准只解除对应记录、预约／代办／候补校验一致、历史数据不追罚。
- 二维码至少验证：编码与识别一致、正常登录回跳、非法目标拒绝、跨对象权限、普通角色不能领还核验。
- G3 至少验证：重复调度防重、停机／预约冲突仲裁、暂停恢复计时、关闭后停止提醒、验收权限与安全阻断。
- 真实浏览器登录及验证码沿用用户手动登录；没有实际执行的角色流程、故障窗口或设备相机验证如实标注。
