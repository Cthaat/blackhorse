## 1. 项目章程

### 1.1 项目定位

本项目面向高校实验室，解决设备档案分散、预约冲突、安全准入核验困难、领用归还不可追溯、维修过程不闭环和隐患整改缺少复查记录等问题。

系统基于RuoYi-Vue Spring Boot 3分支进行二次开发，复用认证、RBAC、菜单、字典、日志、代码生成和Quartz等基础能力。原创工作集中在实验室业务建模、预约并发控制、业务状态机、对象级数据权限、维修验收和隐患整改闭环。

### 1.2 人员与职责

| 参与者 | 职责 |
|---|---|
| 学生开发者 | 项目管理、需求、设计、前后端开发、测试、部署、文档和答辩材料 |
| 用户/需求确认人 | 确认范围、审阅文档、批准变更和最终验收 |
| 指导教师 | 学术与答辩指导、阶段评审；不作为日常编码资源 |

### 1.3 约束

- Java 17、Spring Boot 3、单套响应式Vue 3 Web；
- 前后端分离、模块化单体，不采用微服务；
- MySQL作为事实数据源，Redis只承担缓存、幂等和短期互斥；
- 不依赖真实门禁、物联网、短信、付费云服务或学校内部接口；
- 所有核心业务必须具备可重复执行的测试和演示数据；
- 项目必须在4～6周内形成可答辩版本，以6周计划为正式基线。

### 1.4 成功标准

1. 五类角色按权限使用系统，菜单权限和对象数据权限均有效。
2. 预约使用、维修、安全巡检与隐患整改闭环均可演示。
3. 同设备同区间并发预约最多产生一条有效记录。
4. 资格、设备和隐患阻断规则正确。
5. 空库初始化、自动化测试、发布构建和备份恢复通过。
6. 阻断级、严重级缺陷为零。
7. 需求、设计、接口、数据库、测试、部署和答辩资料齐全。

## 2. 目标、非目标与优先级

### 2.1 目标

- 建立实验室、设备、安全资格的统一档案；
- 实现受事务和并发控制保护的预约使用流程；
- 实现异常归还、故障维修和管理员验收；
- 实现巡检任务、隐患整改和安全员复查销号；
- 实现部门、实验室、本人和工单归属的数据范围；
- 实现站内消息、超期任务、基础统计和状态追溯；
- 形成论文图表、测试数据和答辩演示证据。

### 2.2 非目标

V1不建设小程序、独立H5、真实硬件、AI识别、在线考试、定位、人脸、付费通知、支付、第三方SSO、复杂工作流、微服务、消息队列、多租户、云存储强绑定和生产级高可用。

### 2.3 优先级

| 级别 | 内容 | 处理原则 |
|---|---|---|
| P0 | 登录权限、数据库迁移、实验室设备、资格、预约使用、维修、巡检隐患、状态历史 | 不允许削减 |
| P1 | 站内消息、定时任务、基础工作台、接口文档、自动化测试、部署材料 | V1发布必须具备 |
| P2 | 二维码、Excel、独立大屏、MinIO、丰富消息设置 | P0和P1全部通过后才实施 |

## 4. 六周里程碑

### 第1周：可运行基线

- 固定上游后端和前端提交，记录许可证和版本；
- 建立ruoyi-lab、前端菜单、权限标识和统一业务异常；
- 建立Flyway首版、字典、角色和演示账号；
- 验证登录、空库初始化、前后端测试及生产构建。

**M1验收：** 初始化账号可以登录并看到授权菜单，业务模块接口可鉴权访问，空库迁移成功。

### 第2周：资产与安全准入

- 完成实验室、设备和附件；
- 完成安全资格授予、有效期和范围校验；
- 完成部门及实验室数据范围。

**M2验收：** 学生只见授权设备；有效、过期和范围不符三类资格结果正确。

### 第3周：预约使用闭环

- 完成可预约时段、申请、行锁冲突和幂等；
- 完成审批、驳回、取消、过期、爽约；
- 完成领用、正常归还、异常归还和状态历史；
- 完成20线程并发测试。

**M3验收：** 第一条主流程完整，数据库没有重叠有效预约。

### 第4周：维修与安全闭环

- 完成故障、维修分派、处理和验收；
- 完成巡检计划、任务、检查项；
- 完成隐患整改、多轮复查和销号。

**M4验收：** 维修和第二条主流程完整，重大隐患阻断及解除均有效。

### 第5周：通知、任务、统计与联调

- 完成站内消息和消息中心；
- 完成预约过期、爽约、巡检生成、任务及整改超期；
- 完成基础工作台；
- 执行五角色权限和跨模块联调。

**M5验收：** 全部P0、P1功能集成运行，定时任务可重跑且越权请求全部拒绝。

### 第6周：质量收口

- 完成自动化、并发、安全、性能和端到端验证；
- 完成打包、空库部署、升级迁移、备份恢复；
- 修复全部阻断级和严重级缺陷；
- 完成用户手册、部署手册、测试报告、演示脚本及论文图表。

**M6验收：** 发布候选版本通过需求规格说明书全部验收项。

### 4.1 四周压缩策略

若实际只能使用4周：

- 第1周合并完成M1和M2；
- 第2周完成预约、审批、领用归还；
- 第3周完成维修、巡检和隐患；
- 第4周只做消息最小实现、四项基础统计、测试、修复和交付；
- 全部P2停止，P1只保留验收直接需要的展示；
- 不削减并发、权限、事务、状态历史、两条主流程及其测试。

## 5. 资源与环境

### 5.1 人力

项目由一名学生开发者独立完成。用户或指导教师只承担需求确认和阶段评审，不作为编码产能。

### 5.2 开发环境

- Windows 10或11、PowerShell；
- JDK 17、Maven 3.9；
- Node.js维护中的LTS版本；
- 前端使用上游仓库已有的包管理器和锁文件，禁止混用npm、pnpm或yarn；
- MySQL 8、Redis 7；
- IntelliJ IDEA、Visual Studio Code、Git；
- Edge或Chrome；
- JUnit 5、Mockito、MockMvc及与锁定前端兼容的测试框架。

### 5.3 配置与数据

- 开发、测试和演示使用独立数据库；
- 提供环境变量示例，不提交真实凭据；
- 演示数据全部虚构；
- 上传文件位于Web根目录外，通过鉴权接口下载；
- 每周建立可运行标签和数据库备份。

## 6. Git与质量门禁

### 6.1 分支

- main：只保存通过发布验收的稳定版本；
- develop：开发集成分支；
- feature/WBS-name：按工作包开发；
- fix/issue-name：缺陷修复；
- release/v1.0.0：发布收口。

禁止直接在main开发。已执行的Flyway迁移只允许追加新版本。提交采用Conventional Commits，每个提交只处理一个目的。

### 6.2 合并门禁

每次合并前必须满足：

1. 后端完整验证成功；
2. 前端依赖锁定安装、代码检查、测试和生产构建成功；
3. 新接口具有权限、校验、错误码和OpenAPI说明；
4. 数据库变更使用Flyway，并能在空测试库执行；
5. 无密钥、真实个人信息、调试口令和无关生成文件；
6. 关键业务具有正向、反向和边界测试；
7. 差异经过自审，无无关重构和大范围格式化。

### 6.3 发布门禁

- 全部P0、P1通过验收；
- 两条主流程和维修子流程端到端通过；
- 五角色对象级越权测试通过；
- 并发预约、幂等和定时任务重跑测试通过；
- 空库安装和已有库升级成功；
- 阻断级、严重级缺陷为零；
- 发布包、演示数据、配置示例和文档齐全。

## 7. 测试与验收策略

| 层级 | 重点 |
|---|---|
| 单元测试 | 区间冲突、资格、状态机、隐患阻断、维修验收 |
| 数据库集成 | Mapper、事务回滚、行锁、约束和Flyway |
| 接口测试 | 鉴权、对象数据权限、参数、错误码和业务命令 |
| 前端测试 | 权限显示、状态映射、表单校验和关键工具函数 |
| 并发测试 | 20线程同设备同区间，最多一条有效预约 |
| 安全测试 | 对象越权、非法附件、路径穿越、注入输入和敏感信息 |
| 端到端测试 | 两条主流程及维修验收 |
| 部署测试 | 空库、升级、配置缺失、备份和恢复 |

验收证据包括自动化测试报告、并发结果、权限矩阵、演示截图或录像、迁移日志、构建日志和最终验收清单。

## 8. 风险登记册

| 编号 | 风险 | 概率 | 影响 | 应对 |
|---|---|---:|---:|---|
| R1 | 若依Spring Boot 3后端与Vue 3前端版本不完全兼容 | 中 | 高 | 第1天完成兼容探针；固定提交和锁文件；问题超过1个工作日则保留后端契约并适配已选Vue 3端 |
| R2 | 五角色和多模块造成范围膨胀 | 高 | 高 | 冻结P0、P1；P2默认取消；新增功能必须删除等量范围或进入V1.1 |

| R4 | 状态不完整导致非法跳转 | 中 | 高 | 使用明确迁移表和命令接口；统一状态历史；非法跳转返回409 |
| R5 | 菜单正确但对象数据越权 | 中 | 高 | 服务层强制范围，不能信任前端用户ID；主要接口增加跨部门测试 |

| R7 | 隐患影响范围模糊 | 中 | 高 | 强制实验室级或设备级目标；重大且未销号才触发阻断 |
| R8 | 附件上传或下载带来安全问题 | 中 | 高 | 类型、MIME、大小和路径校验；随机名；对象级下载鉴权 |
| R9 | 文档、接口、字典和状态名称不一致 | 中 | 中 | 状态编码单一来源；每周同步需求追踪和接口文档 |
| R10 | 单人后期没有测试与文档时间 | 高 | 高 | 每个切片同时完成测试文档；第6周停止新增；每日小提交 |
| R11 | 演示环境或数据被污染 | 中 | 高 | 演示数据重置、离线依赖、预构建发布包和恢复演练 |
| R12 | 为答辩亮点引入过度设计 | 中 | 中 | V1只使用单体、事务、Redis和Quartz；新中间件默认进入V1.1 |

## 10. 变更管理

1. 已批准的需求、策划书和验收清单共同构成V1基线。
2. 变更必须记录原因、价值、影响模块、工时、测试和交付影响。
3. 一级变更不改变接口、数据库和验收，且不超过4小时，由开发者记录后实施。
4. 二级变更涉及数据库、接口、状态机或0.5～2天工作量，必须获得需求确认人批准。
5. 三级变更新增角色、终端、外部系统、硬件、中间件或超过2天，默认进入V1.1；纳入V1时必须删除等量原范围。
6. 第2周结束后冻结核心实体、角色和主流程。
7. 第5周结束后进入发布冻结，只修复缺陷、补充测试和完善交付。
8. 变更必须同步需求编号、数据库、接口、测试和验收，禁止只修改代码。

## 11. 决策记录

| 决策 | 结论 | 原因 |
|---|---|---|
| 项目方向 | 实验室设备共享预约与安全巡检 | 现实依据、技术含量、演示效果和个人可完成性平衡最佳 |
| 项目周期 | 4～6周 | 用户选择精简周期，以6周作为风险可控基线 |
| 前端形态 | 单套响应式Vue 3 Web | 减少双端重复开发 |
| 后端底座 | RuoYi-Vue Spring Boot 3分支 | 复用通用权限能力，集中完成原创业务 |
| 架构 | 模块化单体 | 满足规模且避免微服务过度设计 |
| 一致性 | MySQL事务和设备行锁为最终依据 | Redis不能替代数据库正确性 |
| 文件 | 本地存储端口和受控下载 | 避免云厂商绑定和密钥风险 |
