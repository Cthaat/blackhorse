## 一、求职定位与现有基础

以下基础来自当前代码及已落地界面；本次同步 G1 实施记录，不是全项目全量验收，不能直接等同于全部验收通过：

| EXT-41／P1／M | 无 Docker 的版本化发布与运行配置检查 | 产物版本／提交号、启动前配置检查、迁移兼容策略、健康就绪、停机排空；沿用现有脚本与手动部署 | 运维页只读展示版本、运行模式、依赖健康；敏感配置只显示已配置／未配置 | 新环境按 README 可启动；部署失败可恢复到兼容版本；数据库回滚不能靠删除 Flyway 历史或盲目降级。展示工程交付与恢复意识 |

## 四、首选需求的可执行验收边界

以下用例定义各期验收目标。G1、G2 已执行的最小验证见第五节状态表及关联实施记录；未记录为实测的用例仍是验收目标，不是已经获得的测试结果。

### 4.1 EXT-11＋EXT-28：开放日历、候补与规则版本

- 先限定为“单设备、单时段预约”，不同时引入 EXT-13 组合排程。提交、候补转正、改期都走相同资格／冲突／隐患校验；模拟结果不构成预约承诺。
- 候补使用确定性排序：进入队列时间加唯一编号。取消后一次只给一个符合条件的人发送限时确认邀请；邀请只保护该候补确认机会，不代表已有预约获批，仍执行原审批规则。
- 邀请期内对该时段建立可到期的占位；候补占位与普通预约共用数据库仲裁。拒绝／超时／资格失效后释放并重新选人；新申请不能绕过有效占位。具体持续时间作为规则配置。
- 最小并发目标：20 个用户同时竞争同一设备相同时段，最多建立一个有效占用；初始空闲且请求均合法时应有一个成功。相邻但不重叠的时段仍可预约；相同幂等键与相同请求返回原结果，换请求内容明确拒绝。
- 规则发布展示对待执行预约的影响，但不静默批量取消。既有预约保留规则快照；领用时仍检查当前资格、设备状态和安全阻断，历史版本不能成为绕过安全条件的理由。
- 前端同时显示开放时间、占用／候补状态、规则摘要、本人队列状态及确认倒计时；不能显示其他申请人的私人信息。

### 4.2 EXT-29：业务事务成功，通知可以恢复

- 事件有业务对象、事件类型、版本和稳定去重标识；业务事实与待投递事实必须有可靠的持久关联。先评估扩展现有事实补偿是否足够，再决定新增 Outbox，不并行维护两套互相冲突的状态源。
- 交付语义为至少一次投递＋幂等业务效果。业务回滚不发成功事件；投递失败不回滚已提交的预约／维修；同一事件重复消费不重复建站内消息或改变业务状态。
- 覆盖“提交后、投递前退出进程”和“消费成功、确认前退出进程”两种故障窗口；恢复后可以补投或去重，失败到达上限进入待人工处理状态。
- 投递中心只能重放已存在的合法事实，不允许编辑载荷伪造业务操作；重放记录操作者、原因和结果。与现有定时补偿共用去重规则。

### 4.3 EXT-30：异步任务状态、权限与恢复

- 生命周期至少包括待执行、执行中、取消中、已取消、成功、部分成功和失败。重试新建可追溯的执行批次，不把上次失败日志覆盖掉。
- 先确定导入“预检后按批提交”的语义：已提交批次保留，后续取消只阻止后续批次；错误行可下载，重复业务键不能因重试生成重复资产。
- 入队、执行、下载均校验权限。任务绑定提交者和当时筛选条件，执行时范围不得超过提交时与当前权限的交集；下载时权限已撤销则拒绝，不能凭任务编号访问其他人的文件。
- 配置文件大小、行数、队列长度、工作线程数、单人并发和结果保留期限；队列满明确拒绝／提示重试，不无限堆积内存。
- 中途停止后台、重启、取消、重复提交都能在页面看到真实状态；结果文件私有存储，CSV／Excel 输出处理公式注入。

### 4.4 EXT-34：从现象定位到请求与任务

- 至少覆盖 HTTP 请求量／错误／P95、JVM 内存、数据库连接池、待投递事件数／最老积压时间、异步任务成功／失败／耗时；展示采集时间，采集失败不显示伪造的零值。
- 日志、请求响应中的错误关联号、业务历史和异步任务能够关联；不把用户 ID、业务单号等高基数字段当作无限扩张的指标标签。
- 健康详情和业务运维页只允许相应管理员访问；新增管理接口必须兼容项目已有安全配置，不能假定框架会自动替已有自定义规则保护端点。
- 告警第一版只在本机／站内展示；真实邮件、短信、企业消息启用仍需 EXT-16 的配置与授权。

## 八、进入开发的最低确认项

每一期确定本期编号、角色闭环、外部资源、是否允许真实发送／收费／控制设备。确定后细化本期数据模型、接口、状态流转及兼容迁移，再开发前后端；不要求先批准后面全部候选，也不在每个普通实现步骤反复确认。

G1、G2 已有前后端代码、数据库迁移及最小运行验证；G2 仍需继续真实角色页面验收，不代表全量 E2E 或所有故障窗口已验证。G2 复用现有依赖，未启用第三方账号、收费、对外发送或敏感数据传输。后续按需求编号记录“候选／已选定／开发中／已实现待验收／已验收”，并注明验收层次，不能用“需求池已写完”替代“产品已开发完成”。
